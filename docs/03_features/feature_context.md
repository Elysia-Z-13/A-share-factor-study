## 一、四类上下文特征的适用性

| 类型 | 适用 | 理由 | 注意 |
|---|---|---|---|
| Carry 与期限结构 | ⊘ 不适用 | A 股股票无期限结构（无近月/远月之分） | 若未来做期货/期权，连续合约拼接规则必须写进契约 |
| 跨资产与期权 | ⊘ 不适用 | 我们的数据只有 A 股个股行情，无期权/期货/跨市场数据 | 若引入，lead-lag 必须做真实性检验，否则是伪相关 |
| 基本面 | ✅ | 本项目 5 个因子全部来自财报 | 核心要求：用公告日 ann_date，不用报告期 end_date |
| 日历与宏观 | ⚠️ 部分 | 日历特征可用（白名单内）；宏观不用（无 vintage 数据） | 日历只能用事前可知项；宏观必须 vintage |

## 二、基本面：公告日对齐（G-F3.1）

**规则**：对每个 (code, T)，取「ann_date ≤ T」的候选集中 end_date 最大的那一期。

```python
pd.merge_asof(daily, fin, left_on='date', right_on='ann_date',
              direction='backward',  # 只取公告日 <= 当天
              allow_exact_matches=True)
```

**为什么不能用 end_date**：报告期结束 ≠ 市场知道，差 1~4 个月。
D2 对照实验实测：错用时点使 IC 虚高 1.78 倍（0.00774 → 0.01382）。

**实测**：
- 对齐后行数 1,146,358
- 前视违规（ann_date > date）0 行 ✅
- 非公告日值变化 0 次 ✅
- 财报覆盖 88.4%

## 三、修订版本处理

**规则**：保留所有版本，不预先去重；merge 时按 ann_date 时间过滤，
自然得到「当时可见的那一版」。

**实测**：同一 (code, end_date) 有多个版本的组数 = 0，涉及 0 行。
这些行全部保留在财报表中，不做预去重。

**反例**：如果先用 `dedupe_revisions()` 取最终版再 merge，
2024-06-15 就会用上 2024-08-20 才更正的值 → 前视。

## 四、日历特征白名单（G-F3.2）

| 特征 | 含义 | 为什么事前可知 |
|---|---|---|
| `dow` | 星期几 | 永远可知 |
| `month` | 月份 | 永远可知 |
| `is_month_end` | 是否月末 | 日历可推导 |
| `is_quarter_end` | 是否季末 | 日历可推导 |
| `days_to_deadline` | 距法定披露截止日天数 | 《证券法》规定年报 4/30、半年报 8/31、三季报 10/31，事前可知 |

**禁止使用**：

| 禁止项 | 为什么 |
|---|---|
| 实际公告日 | 事前不知道公司哪天公布 |
| 指数调整成分 | 名单调整前不公开 |
| 临时休市日 | 事后才知道（如 2020 春节延长） |

**「财报日前后」的安全用法**：
❌ 用「实际公告日 ±5 日」（事前不知道哪天公布）
✅ 用「法定披露截止日前 10 日」（4/30 是法规截止日，事前可知）

## 五、宏观：声明不使用（G-F3.3）

- 是否使用：**否**
- 理由：无 vintage 数据源；免费数据只给最终修订值，用它会前视
- 若未来引入：必须用首次发布值并在发布日对齐

**为什么必须 vintage**：GDP 数据会被反复修订（初值 4.5% → 修订 4.7% → 终值 4.6%）。
用终值等于在 2024 年 4 月知道了 2025 年的修订结果。

## 六、已知局限

1. 未使用 carry / 跨资产 / 期权特征（数据与工具链不支持）
2. 未使用宏观特征（无 vintage 数据源），这意味着我们放弃了宏观择时维度
3. 日历特征未实际构造为信号（白名单仅作规范，未用于本项目因子）
4. CSMAR 的 DeclareDate 早期年份缺失，导致正确 PIT 下覆盖率降至 61.5%
